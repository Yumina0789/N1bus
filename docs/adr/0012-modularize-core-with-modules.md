# 0012 本体模块化：KMS 与 Harness 搬出去，模块逻辑留在自己的进程里

## 状态

已接受（2026-10-11）

## 背景

面板的「模块」页（原「扩展功能」）下只有两个子视图：KMS 与 Harness。两块都**硬编码**
在本体里 —— KMS 是 `KMSService` + `KMS_WRITES` + `/api/kms*` + 一个 `sub-kms` 页面
（`n1bus.py` 里 6 处分散点、`ui.html` 里约 80 行 JS），Harness 是 `/api/dsh` + 一个
`#dshFrame`。

想加第三个功能，就得改两处源码、重新部署一遍。而这两块本身也不是「服务器管理」的
内容 —— 一个是 KMS 授权服务，一个是 agent 工作台，它们**寄生**在面板里。

主人要求：除 KMS 与 Harness 之外，面板该有的功能全部留在本体；把这两块搬出去，
做成可以装、可以选接不接的**模块**。

## 决策

1. **本体（core）** = N1bus 自己：认证与安全底线、观测、白名单动作、文件管理器、任务、
   告警、审计，**外加模块框架**。KMS 与 Harness 不在本体里。
2. **模块（module）** = 一份 manifest + 可选 compose + 可选页面声明，从受信 registry
   （`N1bus-modules`）装，**整体 sha256 即身份**。
3. **模块的逻辑全在它自己的进程里**（自己的容器）。本体对模块只做五件事：
   编排容器、读容器日志、代理模块的 HTTP API、渲染模块声明的页面、iframe 嵌模块自己的 UI。
4. **装与接分离**：装完是「未接入」；主人打开开关才出现在「模块」页。接入只影响界面，
   不影响容器跑不跑。
5. 本体新增四个受控白名单动作 `module.install/start/stop/restart`，argv 由本体拼死。

## 备选方案

1. **模块自带 Python 代码，本体 import 它**：最灵活，模块能直接挂接口、改渲染。
   否掉的理由 —— 那等于把「任意代码执行」请回面板里，而 ADR 0002 的整个立论就是
   「能改系统的全部手段就是那张 ACTIONS 表」。装一个模块就等于让它以 root 跑在
   systemd 单元里，哈希校验只能保证「装的是我批准的那份」，不能保证那份是安全的。
2. **纯声明式，模块连进程都没有**：最安全，但 KMS 这种必须有个真服务端（RSC4D）
   在监听 1688 的场景表达不了 —— 它需要的恰恰是「把一个服务编排起来」。
3. **不模块化，继续硬编码**：每加一个功能改两处源码 + 重新部署，且新功能与
   「服务器管理」这个主题越走越远。

## 后果

**好的**

- ADR 0002 **不需要修改**：本体仍然不执行任何模块提供的命令，模块的代码跑在它自己的
  容器里，本体只是编排它。
- 加功能变成「往 registry 提一个包」，不再动本体源码。
- KMS 换实现（vlmcsd → RSC4D）不再牵动本体。

**代价**

- 本体多出一整块职责：模块框架（编排 / 日志 / 代理 / 渲染 / iframe）。这是本 ADR 的
  主要成本，也是 `docs/modules.md` 存在的原因。
- `page.kind = declared` 的模块只能表达六种块；复杂界面要退回 `iframe`。
- `aggregate` 块的正则来自外部内容，必须当**不可信输入**处理（长度上限、限制回溯、
  限制输入行数）—— 否则一个恶意正则可以拖死面板。
- 内置模块（kms / harness）的 compose **不搬家**：它们在服务器上各有自己的目录
  （`/opt/nimbus/docker/`、`/opt/dsh/`），换目录会重建容器、KMS 客户端要断约 10 秒。
  所以内置模块的路径来自本体里的固定常量。
