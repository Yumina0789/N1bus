# 0005 封禁状态由服务端判定

## 状态

已接受（2026-10-09）

## 背景

「失败来源排行」是一个按失败次数排序的 IP 榜，每行原本都挂一个「封禁」按钮。问题是
**这个榜单不知道谁已经被封了**：同一批 IP 会一直排在前面，用户（以及 v1m-dash 的自动执法）
封过一次之后再看，界面没有任何变化，于是很容易再点一次。审计里留下的痕迹很直白：

    ufw.deny  deny from 109.160.32.137  Rule added
    ufw.deny  deny from 109.160.32.137  Skipping adding existing rule

`sleep` 一行是重复操作，没有报错、没有提示，纯属白点。

「已被封」这件事有两个真实来源：ufw 的 DENY 规则，和 fail2ban 各 jail 的 Banned IP list。
自动执法（v1m-dash 判定 → N1bus 执行）走的是 `ufw deny from <ip>`，所以 ufw 里能看到它。

## 决策

**由服务端判定并返回结构化结果**：`/api/security` 增加 `blocked` 字段，形如
`{"109.160.32.137": "ufw", "115.140.161.61": "fail2ban/sshd"}` —— 键是 IP，值是"谁挡的"。

前端据此渲染：安全页显示「已封禁 / 未封禁」，已封禁的行把按钮换成**解除封禁**
（ufw 的走 `ufw.undeny`，fail2ban 的走 `fail2ban.unban` + 对应 jail）；概览页只打标记、不放动作。
封禁与解封动作成功后都重新拉一次安全数据。

判定放在服务端而不是前端解析 `ufw status` 文本，是因为：ufw 的输出格式与本地化不定、
fail2ban 还要按 jail 逐个查；这些已经在后端有现成调用，前端只需要一份事实。

## 后果

* 好的一面：同一个 IP 不会再被重复封；被封的 IP 还能一眼看出是 ufw 挡的还是某个 jail 挡的；
  自动执法封掉的 IP 同样会显示「已封禁」。
* 差的一面：`/api/security` 每次多跑一条 `ufw status`（fail2ban 的结果复用同一次响应里已有的
  `fail2ban()`，不重复调用）。这个接口 15 秒轮询一次，代价可接受。
* 差的一面：`blocked` 只是"此刻"的快照，`ufw` 未安装或被停用时它只反映 fail2ban —— 所以
  界面里仍保留 ufw / fail2ban 的原始规则输出，供人工核对。

## 备选方案

1. **前端解析 `firewall.rules` / `raw`**：省掉后端改动，但 `raw` 被截断到 2500 字符，
   DENY 规则常常排在后面，会漏判；而且要把 ufw 的文本格式硬编码进前端。
2. **维护一张"我封过谁"的本地表**：只能记住面板自己封的，记不住手动 `ufw deny` 与
   v1m-dash 自动执法的结果，与实际状态脱节。
3. **不做标记，靠确认弹窗挡重复**：确认框每天点十次就变成无脑回车，挡不住。
