# 0013 计划任务改为可写脚本 + 系统 crontab（修订 0002 / 0006）

## 状态

已接受（2026-10-11）

> **实现状态：未实现**。本 ADR 只定方向 —— 当前代码里的计划任务仍然是
> 「面板自己的一张表，只跑白名单动作」（`n1bus_tasks.py`），既不写脚本也不碰 crontab。

## 背景

ADR 0006 把计划任务做成「面板自己的一张表：把某个白名单动作按周期跑起来」，
理由是不引入 shell、不引入文件写入（承接 ADR 0002）。实机用下来这个形态不好用：
只能从 30 个白名单动作里挑一个，参数还得照该动作的校验器填。想表达「一段自己的逻辑」
（清理几个目录、调一次接口、串两步操作）根本做不到。

用户的原话是「默认提供的不太好用，应该是类似默认启动某个文件那种，类似 1Panel」，
并明确要求：**能写脚本、由系统 crontab 调度**。

## 决策

**计划任务改为「脚本 + crontab」两段式：**

1. 面板负责生成与编辑**脚本文件**（落在数据目录下，0600，属主 root）；
2. 面板负责写入**系统 crontab**（或 `/etc/cron.d/` 下的一个文件）来按周期调用它；
3. 界面上保留现有的启停、立即执行与执行记录。

## 后果

**这是一次安全模型的倒退，必须记账：**

- ADR 0002 的全部立论是「面板能改系统的全部手段就是那张 `ACTIONS` 表」。脚本可写之后
  这条不再成立 —— 面板重新拥有了**任意命令执行**能力。ADR 0002 的「后果」一节
  **早就预言过这一幕**（「届时会有人提出『只增加一个 exec』—— 必须坚持否决」）。
- 因此 **ADR 0002 与 ADR 0006 由本 ADR 修订**：0002 里「v1 不提供任意命令执行」的结论
  在计划任务这一条上被推翻；0006 里「不写系统 crontab、不落任何脚本文件」被推翻。
  两条 ADR 的其余部分仍然有效。
- **实现时必须一并落地的缓解措施**：
  - 脚本与 crontab 文件的写入**仍然只走白名单动作**（argv 写死、路径由本体算），
    不开放任意路径写入；
  - 每一次脚本编辑与 crontab 变更都**写审计**；
  - 界面上明确标注「此功能等同于在服务器上执行任意命令」；
  - 面板的定位随之改变：它不再是一个「只读 + 白名单动作」的面板，而是**完整的 root
    控制台** —— 对外暴露的风险等级要按这个重新评估（尤其见 README 里
    「不要绑 0.0.0.0 / token 是唯一防线」那段）。

## 备选方案

1. **维持现状（只跑白名单动作）**：最安全，但用户明确说不好用。否掉。
2. **只扩充白名单动作的数量与参数自由度**：能覆盖一部分需求，但仍表达不了「一段自己的
   逻辑」。可作为过渡，不能替代脚本。
3. **把脚本能力做成「新的、单独鉴权的组件」**（ADR 0002 最后一句的思路）：例如一条独立的、
   需要二次口令的执行通道。比裸写脚本安全，但更复杂；用户已选择接受取舍，
   本 ADR 不强制，留作后续加强项。
