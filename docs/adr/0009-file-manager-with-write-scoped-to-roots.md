# ADR 0009：文件管理器带写权限，但只限白名单根内

- 状态：已采纳
- 日期：2026-10-10

## 背景

面板原来只有「只读浏览」：在白名单目录里列目录、看文本尾部。用起来最常撞的墙是
"只是想修改一下这个配置文件" —— 而这正是 SSH 的用途，因此最初未提供该能力。

实际使用中（尤其这台机器上运行了 DSH 容器之后），"修改一行配置再重启"成为高频操作：
`/opt/dsh/.env` 更换 key、`/etc/caddy/Caddyfile` 调整反代、查看 `/var/log` 中的日志……
每次都需要登录 SSH，操作体验被割裂为两段。

于是要给它加写能力。这直接撞上 ADR 0002 的精神：**面板不提供任意操作**。

## 决策

**加写，但路径闸门和读一样紧，且每次写都进审计。**

具体：

1. **根内是唯一合法区域**。写路径 `realpath` 之后必须落在某个白名单根之内 ——
   与只读浏览同一套判据。`..`、符号链接、绝对路径花招都逃不掉（有单元测试）。

2. **判父目录而不是判目标**。新建文件时目标还不存在，所以闸门判的是父目录；
   同时禁止直接对白名单**根**下手（否则一条 `DELETE /var/log` 即可删除整个目录树）。

3. **删除分两档**。目录默认只允许删空的；递归删除必须显式带 `recursive`，
   界面上为第二次确认。目的是防止误操作，而非防范恶意行为——能登录面板的人本就具备这些权限。

4. **每次写都审计**，成功失败都写。写法与「白名单动作」一致：
   `file.write` / `file.upload` / `file.mkdir` / `file.touch` / `file.rename` / `file.delete`。
   ADR 0002 说"审计与 danger 无关"，这里沿用。

5. **覆盖前留 `.bak`**。不阻止覆盖（用户明确点的），但给一条后路。

6. **上传走原始 body**，不套 JSON/base64。单次上限 64 MB，超过请用 scp。

7. **不改服务端的读写权限**。N1bus 以 `ProtectSystem=full` 运行，`/etc` 下是只读绑定挂载。
   **没有**为了"文件管理器能改 /etc"去加 `ReadWritePaths` —— 那是加固，不该为了一个
   面板功能削弱它。哪些根此刻可写由 `/api/files` 的 `roots_writable` 如实报告，
   界面把只读的根标出来。

## 后果

- 修改 `/etc` 下的内容仍需 SSH。这是**有意设计**：那些文件最容易导致机器无法启动。
- 面板的可写面 = `/var/log`、`/var/lib/n1bus`、`/opt/nimbus`、`/opt/dsh`。
  `/opt/dsh` 是刻意加进来的 —— 改 DSH 的 key / compose 不必再登 SSH。
- 面板进程仍为 root，因此"能写这四个目录"等同于"能改变这些服务的行为"。这条边界
  与 ADR 0002 的结论一致：**面板进程等同于一个具备 root 权限的 shell，不应直接暴露在公网**。
  认证与来源 IP 白名单是这条边界上唯一的防线。

## 备选方案

- **不做写操作，仅在界面上提供"复制这段命令"**：实现简单，但用户仍需打开终端，问题未解决。
- **做写且不限白名单**：方便得多，但等于把整台机器的读写权交给一个 Web 页面。
  与 ADR 0002 直接冲突，否决。
- **为 `/etc` 放开 `ReadWritePaths`**：可实现界面上"任意内容均可修改"，但代价是失去一层
  对误操作的防护。否决——安全加固优先于便利性。
