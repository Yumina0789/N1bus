# 0007 开屏落位不覆盖用户的选择

## 状态

已接受（2026-10-10）

## 背景

现象：**刷新页面后，趁着页面还没"站稳"，点其它栏目会被弹回主页。**

原因是 `boot()` 的收尾：

```js
await Promise.allSettled([loadOverview(), loadServices(), loadDocker(), ...11 个 loader]);
showView("overview");     // ← 无条件
startPoll();
```

第一行是首屏预热：一次把每个视图的数据都拉好，切过去就是现成的。代价是**它要花时间**，
真机上量到 1~3 秒（`docker stats` 2.5 s、`apt-get -s autoremove` 1.2 s 都在里面）。
第二行在 await 之后才执行，此时主人可能早就点开了「系统」——`showView("system")` 明明生效了，
几秒后被这行无条件的 `showView("overview")` 一句话推翻，页面"就这样自己跳回去了"。

这不是渲染慢或缓存没更新，是**视图所有权之争**：预热和用户的手在抢同一个 `curTab`。

## 决策

**视图所有权归用户；启动流程只在没人接管时才落位。**

* `showView(main, sub, fromUser)` 增加第三个参数，**只有导航点击（nav / 子导航）传 `true`**。
* `fromUser` 为真时置 `viewPinned = true`（主人自己选过了）。
* `boot()` 收尾改为 `if(!viewPinned) showView("overview")`。

预热本身保留 —— 它是首屏体验的来源，问题只在于收尾那一下不该抢方向盘。

## 后果

* 好的一面：刷新后无论手多快，点开的栏目都不会被抢走；同时**没人动手时开屏仍正常落在概览**
  （两条都做了浏览器实测，见下）。
* 好的一面：规则只有一条"用户点过就算数"，以后再加启动期逻辑（自动跳转、恢复上次视图）
  时，照同一条守则写就不会重蹈覆辙。
* 差的一面：`showView` 多了一个容易被忽略的参数。不传 `fromUser` 的调用方**不会**被记为用户选择 ——
  这正是想要的默认值（内部落位不算主人的意思），但新增调用点时要想清楚自己属于哪一类。
* 差的一面：预热期间用户点开的视图，其数据也要现拉（`loadTab`），会和预热的请求抢并发。
  代价是慢一点，不是错。

## 验证方式

用两个本地实例对拍（同一份 `n1bus.py`，一份是旧 `ui.html`，一份是修好的）：

| 实例 | 操作 | 预热跑完后 |
|---|---|---|
| 旧版 | 页面加载 700 ms 时点「系统」 | `curTab=overview`，被弹回主页（复现） |
| 修复版 | 同上 | `curTab=system`，留在原处 |
| 修复版 | 不点，等预热结束 | `curTab=overview`，开屏落位正常 |

为了让时间窗稳定出现，给 `/api/*` 注入 1.2 s 延迟放大预热耗时；真机上这个窗口本来就存在。
脚本：`.whale-tmp/repro_jump.mjs`。

## 备选方案

1. **去掉预热，改成切到哪个视图才拉哪个**：窗口消失，但每次切换都要现等（真机 docker 视图 2.5 s），
   等于把"偶尔跳一下"换成"每次都要等"。
2. **用 `curTab !== "overview"` 判断用户是否动过**：主人点了别的栏又点回概览时就分不清了；
   而且它把"当前视图正好是默认视图"误当成"没人动过"，换个默认视图就会失效。
3. **只缩短预热（加缓存、并发）**：能把窗口从 3 s 压到 0.5 s，但压不到 0 —— 真机上的慢接口永远存在，
   窗口小只是让复现变难。所有权问题得靠所有权标记解决，缩窗口是另一件事（性能表里在做）。
4. **预热不 `await`，立刻落位再让数据陆续回来**：落位确实变快了，但 `showView("overview")`
   依然在用户点击之后执行 —— 只是更难复现，没有修掉。
